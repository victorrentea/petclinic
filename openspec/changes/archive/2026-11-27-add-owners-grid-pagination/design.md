# Design

## Context

- `GET /api/owners?lastName=` → `ownerRepository.findByLastNameStartingWith` → full `List<OwnerDto>`, pets included.
  `Owner.pets` is `LAZY`, so the mapper triggers one pets query per owner (N+1) today.
- `owners` (V1) has `first_name`, `last_name`, `city` as `TEXT` and **no index** besides the PK. The database
  collation is `C.UTF-8`; ICU is available (785 ICU collations in the dev Postgres 16.2, Zonky binaries).
- `ExceptionControllerAdvice` already turns `ConstraintViolationException` into a 400 `ProblemDetail`.
- The frontend already carries an unused `owner-page.ts` with the flat Spring `Page` shape; Angular Material 16.2
  is a dependency (datepicker in use), paginator and sort are not imported yet.
- `openapi.yaml` is generated by `OpenApiExtractorTest`; `api-types.ts` by `npm run generate:api`.

## API contract change — **BREAKING**

`GET /api/owners` always returns one page, never the full list:

```
GET /api/owners?lastName=Po&page=0&size=10&sort=name,asc
→ 200 {"content": [OwnerDto…], "totalElements": 2, "totalPages": 1, "number": 0, "size": 10}
```

| Param | Default | Allowed | Otherwise |
|---|---|---|---|
| `lastName` | `""` (everyone) | case-sensitive prefix | — |
| `page` | `0` | ≥ 0; past the end → 200 with empty `content` and correct totals | — |
| `size` | `10` | 1 – 20 | 400, never silently clamped |
| `sort` | `name,asc` | `name` or `city`, optional `,asc` / `,desc` | 400 naming the allowed keys |

## Technical impact

- **Database**: migration V4 — ICU collation on `owners.first_name`, `last_name`, `city`, plus the sort and
  prefix-search indexes (Decision 6).
- **Backend**: `OwnerRestController.listOwners`, `OwnerRepository`, new `OwnerPageDto` and `OwnerSort`,
  `@BatchSize` on `Owner.pets`; `openapi.yaml` and `ApiExamples.OWNERS` regenerated.
- **Frontend**: `OwnerListComponent`, `OwnerService` (`searchOwners` folds into `getOwners`), `owners.module.ts`
  (Material paginator + sort), the until-now unused `owner-page.ts`, regenerated `api-types.ts`.
- **Consumers of the old list, migrated in the same change**: `OwnerTest`, `AddVisitApiTest`,
  `BasicAuthenticationConfigTest`, `OwnerSearchThroughLatencyProxyTest`, `owners.feature` + `OwnerSteps`,
  `petclinic-test` `OwnersPage`, the JMeter CRUD plan. MCP and the Slack bot do not call this endpoint.

## Goals / Non-Goals

**Goals:**
- One bounded query per page (+ one count, + one pets query) whatever the table size.
- The whitelist of sort keys is enforced by the API, not just by the UI.

**Non-Goals:**
- Case-insensitive search, phone-number normalization, sorting by address / telephone / pets.
- Keyset (cursor) pagination: offset paging is good enough at 100k with indexes; revisit past ~1M.

## Decisions

1. **Explicit `page` / `size` / `sort` request params, not a raw Spring `Pageable`.**
   `size` gets `@Min(1) @Max(20)` (controller is `@Validated`) so the existing advice renders the 400.
   `sort` is parsed into an `OwnerSort` enum (`name`, `city`) × direction; an unknown key throws a validation error
   → 400. *Alternative*: `Pageable` + `@PageableDefault` + `spring.data.web.pageable.max-page-size=20` — rejected:
   it clamps silently instead of answering 400, and accepts any entity property in `sort` (sorting on unindexed
   columns, a 500 on unknown ones).
2. **Total order baked into the enum**: `name` → `lastName, firstName, id`; `city` → `city, lastName, firstName, id`,
   all in the requested direction. Without the `id` tiebreaker, Postgres may return ties in a different order per
   query, which duplicates/drops rows across pages (the 20 identical Kevins proved it locally).
3. **Hand-written `OwnerPageDto`** (`content`, `totalElements`, `totalPages`, `number`, `size`) built from
   Spring Data's `Page`. *Alternative*: serialize `PageImpl` (Spring warns it is not a stable contract) or
   `@EnableSpringDataWebSupport(VIA_DTO)` (nested `page` object, does not match `owner-page.ts`). The flat DTO keeps
   the project rule "DTOs are hand-written" and the shape the frontend already expects.
4. **Repository**: `Page<Owner> findByLastNameStartingWith(String lastName, Pageable pageable)`; Spring Data derives
   the count query with the same filter. `lastName=""` lists everyone.
5. **Pets per page via `@BatchSize(size = 20)` on `Owner.pets`**: the page's owners' pets load in one `IN (...)`
   query. *Alternatives*: `JOIN FETCH` / `@EntityGraph` with paging → Hibernate pages in memory (HHH90003004),
   loading all 100k rows; two hand-written queries (ids, then fetch) → more code for the same SQL.
6. **ICU collation on the columns** (V4 migration): `ALTER COLUMN first_name|last_name|city TYPE TEXT COLLATE
   "und-x-icu"`, then indexes `(last_name, first_name, id)` and `(city, last_name, first_name, id)` serving the two
   orders, plus `(last_name text_pattern_ops)` because an ICU btree cannot serve `LIKE 'Po%'`. JPQL stays
   collation-free. *Alternative*: `COLLATE` in every `ORDER BY` — native SQL, and every future query must remember it.
7. **Frontend: URL is the single source of state.** `OwnerListComponent` reads `ActivatedRoute.queryParamMap`,
   `switchMap`s into `OwnerService.getOwners({lastName, page, size, sort})` (which also replaces today's manual
   "only the latest query answers" unsubscribe), and every pager / sort / search event only `router.navigate`s with
   new query params (page reset to 0 on search, size or sort change). Past-the-end answers trigger a
   `replaceUrl` navigation to the last page. The native `<table>` keeps its markup; `matSort` +
   `mat-sort-header` on Name and City only, `matSortDisableClear` for the two-state toggle; `<mat-paginator>` with
   `[pageSizeOptions]="[5, 10, 20]"` and `showFirstLastButtons`.

## Risks / Trade-offs

- [The Linux Zonky Postgres used in CI may be built without ICU → V4 fails at boot in every test] → the first DB
  task pushes the migration alone and checks CI before anything else depends on it; fallback is a libc collation
  (`"en_US.utf8"`) if the CI image has that locale, otherwise keep `C` order, move the diacritics requirement out
  of this change and open a follow-up.
- [Unfiltered `count(*)` is a full scan] → ~10 ms at 100k, accepted; the content query, the one that grows with
  offset, is the one asserted to use an index.
- [Deep offsets (`page=9999`) get slower linearly] → max page size 20 and a UI that mostly lives on the first pages;
  keyset paging is the escape hatch (Non-Goals).
- [**BREAKING** contract: any external client of `GET /api/owners` breaks] → the only clients are in this repo and
  move in the same change; MCP and the Slack bot do not call it.
- [Changing collation rewrites the three columns] → instant at today's volume; the migration runs before 100k exist.

## Migration Plan

Single deploy of backend + frontend together (the old frontend cannot read a page). Flyway applies V4 on boot.
Rollback = revert the commits; V4 can stay (collation and indexes are harmless to the old code).
