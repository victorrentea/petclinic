# Design

## Context

- `GET /api/owners` → `OwnerRepository.findByLastNameStartingWith(lastName)` → a full
  `List<OwnerDto>`, each owner with its pets (`Owner.pets` is LAZY, so one query per
  owner). There is no service layer: controllers call repositories and mappers directly.
- `owners` columns are `TEXT` in the database's default collation, `C.UTF-8`
  (`V1__core_owners_pets.sql`). Only `pets(owner_id)` and `pets(name)` are indexed.
- `ExceptionControllerAdvice` maps `jakarta.validation.ValidationException` and constraint
  violations to 400, but every other exception to 500. A request parameter that fails to
  bind, such as an unknown enum value, would therefore come back as 500.
- The frontend uses Angular Material 16.2 (datepicker, select, snack-bar) but no
  `MatPaginator`/`MatSort` yet. `owner-page.ts` already declares the page shape.
- Tests start on an empty database. Zonky embedded Postgres gives each test method its own
  copy. The dev database uses the same embedded Postgres 16.2, where `und-x-icu` works.

## Contract and Impact

- **BREAKING** `GET /api/owners` returns one page instead of a JSON array:
  `{content, totalElements, totalPages, number, size}`. It keeps `lastName` and adds `page`
  (0-based), `size` (5/10/20, default 10) and `sort` (`name|city`, `asc|desc`, default
  `name,asc`). An invalid `size` or `sort` → 400 `ProblemDetail`.
- The only caller of `GET /api/owners` is our Angular app. The chatbot and Claude Code reach
  owners only by id, over `/mcp` (`Deployment.drawio.png`; checked in the code). Both
  sides ship in one PR and one deployment.
- **Backend:** `OwnerRestController.listOwners`, `OwnerRepository`, new `OwnerSort` and
  `OwnerPageDto`, `OwnerMapper`, `@BatchSize` on `Owner.pets`, `ExceptionControllerAdvice`
  (400 for a type mismatch), `V4__owner_sort_collation_and_indexes.sql`.
- **Contract artefacts:** `openapi.yaml` (regenerated by `OpenApiExtractorTest`),
  `petclinic-frontend/src/app/generated/api-types.ts`.
- **Frontend:** `OwnerService`, `OwnerListComponent` (state in query params),
  `owner-page.ts` (exists, unused today), `MatPaginatorModule`, `MatSortModule`.
- **Tests:** `OwnerTest` and repository tests, Cucumber `owners.feature`, Playwright
  `owner-search.feature` (its "lists every owner" scenario becomes "lists the first page"),
  `owner-list.component.spec.ts`, `owner.service.spec.ts`.
- **Data:** an optional large demo dataset (~50,000 generated owners) next to "Default".
- **Unchanged:** MCP tools, the chatbot, notification-service.

## Goals / Non-Goals

**Goals:**
- Every query behind the grid is bounded by the page size, and can be served by an index
  at 50,000 owners.
- Sorting, paging and URL state as specified in `specs/owners/owner-list/spec.md`.

**Non-Goals:**
- Changing the search semantics (case- and accent-insensitive search is a separate issue).
- A reusable grid component in `design-system/`, until a second grid needs one.
- Keyset (cursor) pagination: offset paging is fine at 50,000 rows, and the UI needs page
  numbers anyway.

## Decisions

### D1. Explicit request parameters, not Spring's `Pageable` argument
`listOwners(lastName, page, size, sort)` with `sort` as an `OwnerSort` enum (`NAME_ASC`,
`NAME_DESC`, `CITY_ASC`, `CITY_DESC`, bound from `name,asc` …). The enum builds the Spring
`Sort`: `name` → `lastName, firstName, id`, `city` → `city, id`, the direction applying to
every key, `id` included: `city DESC, id DESC` is the `(city, id)` index read backward,
whereas `city DESC, id ASC` could use no index and would sort all 50,000 rows.
*Alternative:* a `Pageable` resolved by `PageableHandlerMethodArgumentResolver`. Rejected:
it accepts any property path (`sort=pets.visits.description` would join), clamps an
oversized `size` silently instead of rejecting it, and its sort syntax would leak entity
field names into the API contract.

### D2. Invalid `size` / `sort` → `ValidationException` → 400
Both are checked in code and rejected with `jakarta.validation.ValidationException`, which
the advice already maps to a 400 `ProblemDetail`. A bad enum value surfaces as
`MethodArgumentTypeMismatchException`; the advice gets a handler for it mapping to 400,
otherwise it would land in the generic 500 handler.
*Alternative:* `@Min/@Max` on `size`. Rejected: the allowed set is {5, 10, 20}, not a range.

### D3. Repository returns `Page<Owner>`
`Page<Owner> findByLastNameStartingWith(String lastName, Pageable pageable)` replaces the
`List` variant, whose only caller is `listOwners`. Spring Data derives the count query.
*Alternative:* `Slice` (no count). Rejected: the paginator shows the total.

### D4. Hand-written `OwnerPageDto`
`{content: OwnerDto[], totalElements, totalPages, number, size}`, built by `OwnerMapper`
from the `Page`. It matches the existing `owner-page.ts` and the house rule of hand-written
DTOs. *Alternative:* serializing `PageImpl` (Spring warns that its JSON shape is unstable)
or Spring's `PagedModel` (shape `{content, page:{…}}`, a framework type in the contract).

### D5. ICU collation on the columns, plus indexes in the sort order
`V4__owner_sort_collation_and_indexes.sql`:
`ALTER COLUMN last_name/first_name/city TYPE text COLLATE "und-x-icu"`, then
`CREATE INDEX ON owners (last_name, first_name, id)` and `CREATE INDEX ON owners (city, id)`.
A plain btree on a non-`C` column cannot serve `LIKE 'x%'`, so the search also gets
`CREATE INDEX ON owners (last_name text_pattern_ops)`.
*Alternative:* `ORDER BY … COLLATE "und-x-icu"` in a `@Query`. Rejected: the indexes would
not match the query's collation, so every page would sort all 50,000 rows.

### D6. Pets and their visits: `@BatchSize(size = 20)` on `Owner.pets` and `Pet.visits`
Each owner row carries its pets, and each pet its visits (`OwnerDto`), so a page of 20 took
42 queries: page, count, 20 × pets, 20 × visits. Batched, a page of up to 20 owners loads
its pets in one `IN (…)` query and their visits in another, 4 in total. *Alternative:* `JOIN FETCH` / `@EntityGraph` on the paged query. Rejected: with
a collection fetch, Hibernate pages in memory (HHH90003004), which loads every owner again.

### D7. URL query params own the grid state
`OwnerListComponent` reads `lastName`, `page` (from 1), `size`, `sort` from
`ActivatedRoute.queryParamMap` and reloads on every change. User actions only
`router.navigate([], {queryParams, queryParamsHandling: 'merge'})`. Search, sort and size
changes drop `page`. The URL is the single source of truth, so Back and shared links work
without extra code. Converting the 1-based URL page to the 0-based API page happens only in
`OwnerService`. Loads keep the existing "only the latest request may answer" rule
(`switchMap` over the query params).

### D8. Past-the-end correction in the frontend
When a response has empty `content` and `totalPages > 0`, the component navigates to
`page = totalPages` with `replaceUrl: true`. The backend stays a plain page lookup.
*Alternative:* the backend clamps. Rejected: then a response would no longer say what was
asked for.

### D9. Material `MatPaginator` + `MatSort`
`mat-paginator` with `[pageSizeOptions]="[5,10,20]"` and `[length]="totalElements"`;
`matSort` on the table, `mat-sort-header` on Name and City only. They are driven from the
URL state (no `MatTableDataSource`: the server already did the slicing).

## Risks / Trade-offs

- [Zonky's Postgres build lacks ICU → V4 fails in tests] → the first task is a test that
  runs V4 on Zonky. If ICU is missing, stop and ask; falling back to `COLLATE` in the
  query is decision D5's rejected alternative.
- [A collation change alters every `=`/`<` comparison on those columns] → `und-x-icu` is
  deterministic, so equality is unchanged; only ordering moves. The existing
  case-sensitive prefix scenarios in `owner-search.feature` must stay green.
- [The contract change breaks the frontend if one side deploys first] → both ship in one
  PR and one deployment; there are no external consumers (see proposal).
- [`OFFSET` grows with deep pages] → at 50,000 / 5 = 10,000 pages, the last page scans
  about 50,000 index entries, which takes milliseconds. Revisit keyset paging only beyond
  about a million rows.
- [The Playwright scenario "lists every owner" no longer holds] → it becomes "lists the
  first page and the total"; its `@generate_sequence` diagram is regenerated.

## Migration Plan

Flyway applies V4 at backend start. Rollback = revert the commit and drop the three
indexes, since a collation change reverted to `C` is harmless. There is no data migration.
