# Design

Decisions marked ✅ were taken by Victor (see `QA.md`); those marked 💡 are Claude's
recommendation, not reviewed yet — change them here before applying.

## Context

- `OwnerRestController.listOwners` returns `List<OwnerDto>` straight from
  `OwnerRepository.findByLastNameStartingWith(lastName)` — no ORDER BY, no limit. There is no
  service layer; the controller talks to the repository and the hand-written `OwnerMapper`.
- `Owner.pets` and `Pet.visits` are LAZY with no batching, and `OwnerDto` carries pets with their
  visits, so today's list is 1 + N + N·M queries.
- `owners` has no index at all besides its PK. Columns are `TEXT`; the dev DB collation is
  `en_US.UTF-8`.
- `openapi.yaml` is generated by `OpenApiExtractorTest` and drift-checked on push; the frontend
  types come from it (`npm run generate:api`).
- The grid is a plain Bootstrap `<table>`; `@angular/material` 16 is installed but neither
  MatSort nor MatPaginator is imported. The design system has only `<app-combo>`.

## API contract

**BREAKING** — `GET /api/owners` always returns **one page**, never the full list:
`OwnerPageDto { content: OwnerDto[], totalElements }`. Query params: `sort=name|city`,
`dir=asc|desc`, `page` (0-based), `size=5|10|20`, next to the existing `lastName` prefix filter.
Any other value is a 400 `ProblemDetail`. Only the Frontend calls this endpoint — checked against
`Deployment.drawio.png` and the code: the chatbot and MCP clients use other endpoints.

## Affected code

- **Backend**: `OwnerRestController.listOwners`, `OwnerRepository`, new `rest/dto/OwnerPageDto`,
  a Flyway migration with the sort/filter indexes, `@BatchSize` on `Owner.pets` / `Pet.visits`,
  `openapi.yaml` (regenerated) and the generated `api-types.ts`.
- **Frontend**: `owners/owner-list` (MatSort + MatPaginator), `owner.service.ts`, a new
  `ownerName` pipe used in 7 templates, the unused `owners/owner-page.ts` deleted.
- **Tests reading the full list**: `OwnerTest`, `owners.feature` + `OwnerSteps`,
  `OwnerSearchThroughLatencyProxyTest`, `AddVisitApiTest`, the JMeter plan; e2e
  `owner-search.feature` glue, `add-visit.dsl.ts`; frontend unit tests of the list and service.
- **Tests reading an owner's name**: e2e specs locating `td.ownerFullName` / `a.owner-link`.

## Goals / Non-Goals

**Goals:**
- Each grid request costs a bounded number of queries on indexes, whatever the owner count.
- One place formats an owner's name.

**Non-Goals:**
- A reusable paginated-grid widget in the design system — wrap one when a second grid needs it.
- Case-insensitive or full-name search — the filter keeps today's semantics.
- Cleaning up the test owners (`Ada Acceptance…`) that accumulate in the dev DB.

## Decisions

**D1 ✅ Same endpoint, always paged, hand-written DTO.** `GET /api/owners` returns
`OwnerPageDto { List<OwnerDto> content; long totalElements }` in `rest/dto/`. Rejected: Spring's
`Page` JSON (unstable, leaks `pageable`/`sort` into `openapi.yaml`), `PagedModel` (contract hidden
behind an annotation), an `X-Total-Count` header (the total vanishes from the contract).

**D2 💡 Opaque sort keys, not column names.** `sort=name|city` and `dir=asc|desc` are parsed into
an enum; the controller maps them to a `Sort` it builds itself. Rejected: Spring's
`Pageable` argument (`sort=lastName,asc`) — it would let any property through, and "any column"
is exactly what we pushed back on. Invalid values → `ValidationException` → the existing
`ExceptionControllerAdvice` 400 `ProblemDetail`.

**D3 💡 Orders and tie-breakers.**
- `name` → `last_name, first_name, id` ✅ (last name first)
- `city` → `city, last_name, first_name, id`
- `dir` flips every key including `id`. The trailing `id` makes the order total, so a page
  boundary never falls between equal rows in a different place on the next request
  (London × 8 in the seed).

**D4 💡 Defaults: `sort=name`, `dir=asc`, `page=0`, `size=10`; sizes limited to {5, 10, 20}.**

**D5 💡 Indexes in a new `V4__owner_grid_indexes.sql`.**
- `(last_name, first_name, id)` — serves the name sort.
- `(city, last_name, first_name, id)` — serves the city sort.
- `(last_name text_pattern_ops)` — serves `LIKE 'Da%'`. Under `en_US.UTF-8` a plain btree cannot
  serve a prefix `LIKE`, and a `text_pattern_ops` one cannot serve `ORDER BY`, hence both.

**D6 💡 `@BatchSize(size = 20)` on `Owner.pets`, `@BatchSize(size = 100)` on `Pet.visits`.** One
query per page for the pets and one for their visits, instead of one per owner. The visits batch
is keyed by pet, and a page of 20 owners holds more than 20 pets (found while applying: 20 split
it in two); on Postgres Hibernate binds the batch as one array (`= any(?)`), so 100 costs nothing. Rejected: `JOIN FETCH` of a collection
with paging — Hibernate then pages in memory (HHH90003004). Rejected: a slimmer grid DTO without
visits — it would fork `OwnerDto`, which the owner record also uses.

**D7 💡 Frontend: `matSort` + `mat-paginator` on the existing table.** Headers for Name and City
only, `matSortDisableClear` (asc ↔ desc, no third "unsorted" state), `[pageSizeOptions]="[5, 10, 20]"`.
Search, sort and size changes reset `pageIndex` to 0. Each change cancels the request in flight
(`switchMap`), keeping the guarantee today's `searchByLastName` gives by hand. Owner types come
from the generated `api-types.ts`; `owners/owner-page.ts` is deleted.

**D8 ✅ One `ownerName` pipe** (`owner | ownerName` → `"McCallister, Kevin"`), declared in a
shared module every owner-showing feature module imports. The Visits list passes a pair of
fields (`ownerFirstName`/`ownerLastName`), so the pipe takes anything with a first and last name.

**D9 💡 Count on every request.** `Page` from Spring Data runs a `count(*)` with the same filter —
milliseconds at 50k rows, and the paginator needs the total.

**D10 ✅ Grid state in the URL** (asked for at the first review, 5 Oct). `sort`, `dir`, `page`,
`size` and `lastName` are query params; only values that differ from the defaults are written, so
`/owners` stays the plain link. The component reads `queryParamMap` as its only source of truth and
every change navigates with `replaceUrl` — Back leaves the screen instead of stepping through each
page, yet Back from an owner's record still lands on the page left. A value the grid does not
offer (`size=1000`) falls back to its default rather than reaching the API's 400.

**D11 ✅ Review polish (5 Oct).** Pets on one comma-separated line with an ellipsis, a ▾ unfolding
them one per line (an `appOverflow` directive shows it only when the line is cut); fixed column
widths (`table-layout: fixed`) so a re-sort never slides the header under the mouse; Name/City
arrows always visible, the active one white; paginator in the table's font with first/last
buttons, on one row with *Add Owner*; *Find Owner* at the end of the search row; no table and no
paginator when nothing matches, a centred message instead.

## Risks / Trade-offs

- [Dev DB already ran another branch's `V4`] → Flyway validation fails on boot. Check
  `flyway_schema_history` first; if a foreign V4 is there, reset once with `./start-database.sh`
  (wipes runtime rows).
- [The server's default collation depends on the host] → under the `C` locale of a CI runner `Ś`
  sorts after `Z`. V4 pins `last_name`, `first_name` and `city` to ICU's `en-x-icu` (bundled with
  the zonky binaries on every platform), so the order no longer depends on how the server was
  initialised — in tests, on CI or in production.
- [Tests read the whole list as an array] → migrated to `$.content` / `totalElements`; e2e helpers
  that scanned all owners to find a pet use `GET /api/pets` (it carries `ownerId`) instead.
- [Parallel e2e suites add owners to one shared DB] → the acceptance scenario asserts order and
  counts, never which names appear.
- [Visible name format changes] → every e2e locator reading `td.ownerFullName` / `a.owner-link`
  text expects "Last, First".

## Migration Plan

Frontend and backend ship together (one repo, one deploy); there is no other consumer of
`GET /api/owners`. Rollback = revert the commit; the V4 indexes are harmless to the old code.
