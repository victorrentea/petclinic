# Design

## Context

See `proposal.md` for the motivation (written for the product owner) and `specs/owner-list/spec.md` for
the behavior. The expected volume is ~50,000 owners within a year (`AGENTS.md`); the decisions come from
`QA.md`, where items 1–8 were confirmed and items 9–25 are adopted here as working assumptions.

The current state that shapes the approach:

- `OwnerRestController.listOwners` calls `OwnerRepository.findByLastNameStartingWith(lastName)` and maps
  the whole `List<Owner>` to `List<OwnerDto>`. No service layer (ARCHITECTURE.md), so paging goes straight
  into the controller and repository.
- `OwnerDto` nests `PetDto`, which nests `VisitDto`. `Owner.pets` and `Pet.visits` are LAZY `@OneToMany`
  sets, so mapping a page of 20 owners today would fire one query per owner and one per pet.
- `owners` (V1) has `TEXT` columns with the database default collation `C.UTF-8` and **no index** besides
  the primary key. `pets(owner_id)` is indexed. Postgres 16.2 from zonky ships ICU (785 collations); so does
  the official `postgres` image used by the Docker stack.
- Spring Boot 3.5.11, so Spring Data supports `@EnableSpringDataWebSupport(pageSerializationMode = VIA_DTO)`.
- `openapi.yaml` is generated by `OpenApiExtractorTest`, and `api-types.ts` from it by `npm run generate:api`.
  Both are checked for drift in CI, as is `docs/generated/DB.sql` (`DbSchemaExtractorTest`) and its `DB.puml`.
- The frontend already depends on Angular Material 16.2 (datepicker, snack-bar), but nothing uses its table,
  paginator or sort yet. `owner-list` cancels a stale request when a newer search starts; that must survive.

## Technical Scope

### API contract — **BREAKING**
- `GET /api/owners` returns one page instead of a bare array:
  `{content: [OwnerDto…], page: {size, number, totalElements, totalPages}}` (D1).
- New query parameters `page` (0-based), `size` and `sort`, next to the existing `lastName` prefix filter.
- `size` defaults to 10 and is clamped to 20 (D6); the grid offers 5, 10, 20.
- `sort` accepts only the keys `name` and `city`, each `asc`/`desc`; anything else is a 400 `ProblemDetail`
  naming the key (D2). No `sort` means `name,asc`. Every order ends with `id` as tie-breaker.
- Readers of the old array: only the Angular Owners grid (updated here). The two health checks
  (`docker-compose.test.yml`, `petclinic-test/start-apps.ts`) look at the status code alone; the chatbot
  reads `/api/specialties/feed` and calls MCP tools that load owners by id (verified against the
  deployment diagram and the code). The JMeter benchmark only POSTs.

### Database
- New versioned migration `V4__owner_list_sorting.sql`: ICU collation `und-x-icu` on `owners.last_name`,
  `first_name`, `city` (D4), and indexes `(last_name, first_name, id)`, `(city, last_name, first_name, id)` (D5).
- Regenerated: `petclinic-backend/docs/generated/DB.sql` and `DB.puml`.
- `db/migration/` and `openapi.yaml` need `@victorrentea/tech-leads` review (CODEOWNERS).

### Frontend
- Grid state lives in the URL: `/owners?page=2&size=10&sort=city,asc&lastName=…` (D7).
- Name column renders "Last, First"; `matSort` on Name and City only; `mat-paginator` below the table.

### Code touched
- Backend: `OwnerRestController.listOwners`, `OwnerRepository`, Spring Data web config,
  `ExceptionControllerAdvice`, `Owner.pets` / `Pet.visits` (`@BatchSize`), `ApiExamples.OWNERS`.
- Frontend: `owner-list` component, `OwnerService`, `OwnersModule`; regenerated `api-types.ts`.
- Generated contract: `openapi.yaml`.

### Tests touched
- Backend: `OwnerTest`, `AddVisitApiTest`, `OwnerSteps` + `owners.feature`,
  `OwnerSearchThroughLatencyProxyTest`, `BasicAuthenticationConfigTest`.
- Frontend: `owner-list` and `OwnerService` specs.
- E2E: `add-owner.spec.ts`, `owner-search.feature` and its glue — the "every owner in the clinic is
  listed" scenario no longer holds once the list is paged.

### Out of scope
- Case-insensitive last-name search (QA.md #16), E.164 telephone normalisation (#25), a reusable paged
  grid in `design-system/` (#15).

## Goals / Non-Goals

**Goals:**
- A page of owners costs a bounded number of SQL statements (page + count + batched pets/visits), whatever
  the table size.
- The first page in either sort order reads an index, not 50k rows; verified with EXPLAIN ANALYZE.
- The API contract exposes sort *keys* (`name`, `city`), not entity property names.

**Non-Goals:**
- A reusable paged-grid component in `design-system/` (wait for a second paged grid).
- Making the last-name search case-insensitive, or making it use an index (it stays a prefix `LIKE`).
- Keyset (cursor) pagination — offset paging is enough at 50k rows and is what the paginator needs.

## Decisions

### D1. The response is Spring Data's `PagedModel`, serialized `VIA_DTO`
`listOwners` returns `PagedModel<OwnerDto>`; `spring.data.web.pageable.serialization-mode=via-dto` selects the
DTO form. Not `@EnableSpringDataWebSupport(pageSerializationMode = VIA_DTO)`: that annotation makes Boot's
`SpringDataWebAutoConfiguration` back off, and with it the `spring.data.web.pageable.*` limits of D6.
*Alternatives:* serializing `Page`/`PageImpl` directly (Spring Data warns its JSON is not stable); a
hand-written `OwnerPageDto` (same shape, one more class); a bare array plus an `X-Total-Count` header
(invisible to OpenAPI and to the generated TS types, needs a CORS expose).

### D2. The API takes sort keys, translated to a fixed `Sort` in the controller
The controller takes the `Pageable` that Spring builds from `page`, `size` and `sort`, then replaces its sort:
`name` → `lastName, firstName, id`; `city` → `city, lastName, firstName, id`; no sort → `name,asc`. The
direction of the requested key applies to every column of its chain except the `id` tie-breaker. Any
other key throws a dedicated exception that `ExceptionControllerAdvice` renders as a 400 `ProblemDetail`
naming the key.
*Alternatives:* letting Spring Data bind raw property names (exposes `telephone`, `address`, `pets` — the
last one fails deep in Hibernate as a 500 — and couples the contract to field names); a `@SortDefault`
annotation (handles the default, not the whitelist or the tie-breaker).

### D3. Pets and visits load in batches, never through a fetch join
`Owner.pets` and `Pet.visits` get `@BatchSize(size = 20)` (the maximum page size). A page then costs: the
owners page, the count, one query for the pets of those owners, one for the visits of those pets (types
are a handful of rows already in the persistence context).
*Alternatives:* `JOIN FETCH o.pets` with a `Pageable` — Hibernate logs HHH90003004 and pages **in memory**,
loading every owner, which is exactly what this change removes; `@EntityGraph` on the paged query (same
in-memory paging for a collection); a global `hibernate.default_batch_fetch_size` (works, but changes fetching
for every entity as a side effect of this change); a slimmer list DTO without visits (a second contract
change the grid does not need).

### D4. Locale-aware order comes from the column collation
A new migration `V4__owner_list_sorting.sql` alters `owners.last_name`, `first_name` and `city` to
`TEXT COLLATE "und-x-icu"` (the ICU root collation: language-neutral, deterministic). Spring Data's
`ORDER BY` picks up the column collation by itself, so no query mentions collations.
*Alternatives:* `ORDER BY … COLLATE` in a custom query (Spring Data `Sort` cannot express it, and a
column index would not serve that order); changing the database's default collation (needs a new
cluster, and would change every table); a language-specific collation such as `ro-x-icu` (the owners
are of many nationalities, so no single language's rules fit).

### D5. Two composite indexes, created in the same migration as the collation
`owners (last_name, first_name, id)` and `owners (city, last_name, first_name, id)`. Each matches one
sort chain from D2 exactly, so `ORDER BY … LIMIT n` reads n index entries. A descending sort scans the
same index backwards, then puts ties in ascending `id` order with a small Incremental Sort (seen in
EXPLAIN). Created after the collation change so they carry the ICU collation.
*Alternatives:* one index per column (the planner cannot serve a multi-column order from them);
no index (a seq scan + sort of 50k rows per click — tens of ms, but it grows with the table).

### D6. Size limits are Spring Data web properties
`spring.data.web.pageable.default-page-size=10` and `max-page-size=20`; Spring clamps larger sizes to 20
instead of failing, which is the behavior the spec asks for.

### D7. The grid reads its state from the URL and writes back only to the URL
`owner-list` subscribes to `ActivatedRoute.queryParamMap` (`page`, `size`, `sort`, `lastName`) and
`switchMap`s each change into `OwnerService.getOwners(query)`, which keeps the "only the latest request
answers" property the component has today. Paginator, sort header and search form never load data
themselves: they only `router.navigate([], {queryParams, queryParamsHandling: 'merge'})`. A search
also sets `page` to 1. The URL's `page` counts from 1, because people read and share it (`page=1` is the first
page); the grid subtracts 1 before calling the 0-based API.
The table keeps its Bootstrap markup and gains `matSort` + `mat-sort-header` on the Name and City `<th>`s
(`disableClear`), with a `mat-paginator` (`[pageSizeOptions]="[5, 10, 20]"`) below it; `MatSortModule`
and `MatPaginatorModule` are imported in `OwnersModule`.
*Alternatives:* component fields as the source of truth with the URL as a mirror (two sources that can
disagree on Back); converting to `mat-table` (rewrites the template and its CSS for no behavioral gain).

### D8. Recovering from a page past the end happens in the grid
When a response has empty `content`, `totalElements > 0` and `page.number >= totalPages`, the grid
navigates to `page = totalPages - 1` with `replaceUrl: true`, so Back does not return to the empty page.

## Risks / Trade-offs

- [The ICU migration rebuilds the column definitions on a live table] → At 50k rows it takes well under a
  second, and it runs at boot before traffic. It is run against the Docker stack's `postgres` image in CI
  e2e, not only against zonky.
- [`LIKE 'Pot%'` on an ICU column cannot use the btree index] → Accepted: a seq scan with a prefix filter
  over 50k rows costs a few ms. If search becomes slow, a `text_pattern_ops` index is the targeted fix.
- [`count(*)` on every page request is a seq scan] → A few ms at 50k; acceptable, and the paginator needs it.
- [An unknown sort key used to be silently ignored, now it is a 400] → Only the grid calls this endpoint,
  and it only sends `name` or `city`.
- [Offset paging shifts rows when owners are added or deleted between clicks] → Accepted for a clinic UI;
  the id tie-breaker keeps the order deterministic at any single moment.
- [The `owner-search.feature` "every owner is listed" scenario contradicts paging] → It is rewritten to
  check the first page plus the reported total.

## Migration Plan

1. Merge with backend and frontend together: the API change is breaking, and the grid is its only reader.
2. Flyway applies `V4` at backend start; no data migration. Seed and reference data are unaffected.
3. Rollback: a forward migration that drops the two indexes and restores the `C.UTF-8` collation, plus
   reverting the code. Flyway has no undo here.
