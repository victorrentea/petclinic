## Context

See proposal.md for motivation. Current state that shapes the approach:

- `OwnerRestController.listOwners` returns `List<OwnerDto>` from
  `OwnerRepository.findByLastNameStartingWith`; `OwnerMapper` maps each owner's lazy `pets`
  (and their visits) one owner at a time — an N+1 that is invisible at 28 rows.
- `OwnerRepository` extends the minimal `Repository<Owner,Integer>`, not `JpaRepository`, so
  paging methods must be declared explicitly.
- `ExceptionControllerAdvice` (scoped to the `rest` package) has no handler for
  `MethodArgumentTypeMismatchException`; the catch-all returns 500.
- `owners` has no index beyond the PK (`V1`). No migration uses `DO $$` blocks yet; tests run
  on Zonky embedded Postgres 2.0.7.
- Angular 16 with `@angular/material` 16.2.1 already a dependency; `MatSnackBar` is wired in
  `HttpErrorInterceptor`. `OwnerService` swallows errors into `[]` via `handlerError`.
  `owner-page.ts` (`OwnerPage`) and the wiremock `get-api-owners.json` already exist in the
  page shape but are unused.
- `owner-search.feature.glue.ts` reads the list as an array, joins names as "First Last" and
  splits Examples cells on `,`.
- `openapi.yaml` is generated by `OpenApiExtractorTest`; `api-types.ts` by `npm run
  generate:api`. Both are drift-checked in CI and pre-commit.

## Interface and artefacts (moved out of proposal.md)

**REST contract — `GET /api/owners`** (BREAKING: was a bare array)
- Returns Spring `Page<OwnerListItemDto>`: `content`, `totalElements`, `totalPages`,
  `number` (0-based), `size`. Never an unpaged list.
- Query parameters: `page` (0-based, default 0), `size` (5 | 10 | 20, default 10), `sort`
  (`NAME` | `CITY`, default `NAME`), `dir` (`asc` | `desc`, default `asc`), `lastName`

## Goals / Non-Goals

**Goals:**
- Every owner-list query is bounded in rows and served by an index at 100k owners.
- One list contract (`Page<OwnerListItemDto>`) that the UI, the e2e glue and the OpenAPI file
  all agree on, regenerated in one commit.
- Grid state fully recoverable from the URL.

**Non-Goals:**
- Keyset pagination (revisit at ~10M rows).
- Removing `GET /api/owners/count`.
- Localising `MatPaginator`.
- Fixing `OwnerService`'s error swallowing for anything but the grid fetch.
- Reconciling `Owner.telephone` validation with the seed data.

## Decisions

**D1. Explicit `page/size/sort/dir` binding over Spring `Pageable`.**
`sort` binds to an inner `enum SortField { NAME, CITY }` on the controller and `dir` to
`Sort.Direction`; the controller builds `PageRequest.of(page, size, sortFor(field, dir))`
where `NAME → Sort.by("lastName","firstName","id")` and `CITY → Sort.by("city","id")`.
Alternative: `Pageable` resolver — rejected because it accepts any property path
(`pets.visits.description`), which becomes a 500 or an unintended join, and documents nothing
in `openapi.yaml`.

**D2. `size` whitelist enforced at the edge.** A `Set<Integer> ALLOWED_SIZES = {5,10,20}`
check in the controller throws a validation error mapped to 400. Alternatives: silent clamp
(hides client bugs) or free-form (re-arms the 100k-in-one-response gun).

**D3. 400 for bad enums.** Add `@ExceptionHandler(MethodArgumentTypeMismatchException)` in
`ExceptionControllerAdvice` building the same Problem Detail shape as the validation handlers,
naming the parameter and the accepted values. Without it a bad `sort` value is a 500.

**D4. Repository API.** `Page<Owner> findByLastNameStartingWith(String lastName, Pageable
pageable)` on `OwnerRepository` (derived query; Spring Data issues the `count(*)` for
`totalElements`). Exact count over `Slice`/estimate: at 100k Postgres counts a filtered index
in milliseconds and the paginator needs `totalPages`.

**D5. Pet names via one explicit query.** `List<Pet> findByOwnerIdIn(Collection<Integer>
ownerIds)` on `PetRepository`; the mapper groups by owner id and sorts names. Alternative:
`@BatchSize` on `Owner.pets` (there is an uncommitted `import BatchSize` in `Owner.java` on
this branch, from someone trying it) — rejected because its effect is only visible in the SQL
log, whereas an explicit query is greppable and shows as a named call in the generated
sequence diagrams. The diagram for the owners page should show exactly two queries per page
(+ the count).

**D6. Separate `OwnerListItemDto`.** Fields: `id, firstName, lastName, address, city,
telephone, petNames: List<String>`. `OwnerDto` keeps `pets` with visits for `GET
/api/owners/{id}`. Alternative: reuse `OwnerDto` with empty `visits` — a field that is
sometimes real and sometimes a lie, which the chatbot would believe.

**D7. Indexes with ICU collation, defensive migration.** `V9__owner_sort_indexes.sql`:
```sql
DO $$ BEGIN
  CREATE COLLATION IF NOT EXISTS owner_name (provider = icu, locale = 'und');
  CREATE INDEX IF NOT EXISTS owners_name_idx ON owners (last_name COLLATE owner_name, first_name COLLATE owner_name, id);
EXCEPTION WHEN OTHERS THEN
  RAISE NOTICE 'ICU unavailable, falling back to default collation: %', SQLERRM;
  CREATE INDEX IF NOT EXISTS owners_name_idx ON owners (last_name, first_name, id);
END $$;
CREATE INDEX IF NOT EXISTS owners_city_idx ON owners (city, id);
```
The `ORDER BY` must use the same collation or the planner cannot use the index for sorting.
With a derived Spring Data query the `ORDER BY` has no `COLLATE`, so the NAME sort needs a
`@Query` (JPQL cannot express `COLLATE`; use a native query with `countQuery`, or put the
collation on the *column* — `ALTER TABLE owners ALTER COLUMN last_name TYPE text COLLATE
owner_name` — so every `ORDER BY last_name` picks it up with no SQL change). **Chosen: column
collation** (inside the same `DO` block, before the index), which keeps the repository a plain
derived query and makes the index usable by any future sort on the column. First implementation
step: confirm on Zonky whether `CREATE COLLATION ... provider = icu` succeeds
(`SELECT * FROM pg_collation WHERE collprovider = 'i'`); if it never does, the ICU branch is
exercised only in real Postgres and the ICU scenario in the spec runs against dev Postgres, not
CI. `EXPLAIN` on the 100k dataset must show an Index Scan on `owners_name_idx` with no Sort node.
**Correction (task 2.6):** the "Smith, Śliwiński, Taylor" example above and in spec.md had the
order backwards — verified against real Postgres ICU, the correct ascending order is
**Śliwiński, Smith, Taylor** (base-letter comparison: "Sliwinski" vs "Smith", second letter
'l' < 'm'). spec.md is corrected; this note stays as a record of the mistake.

**D8. OFFSET paging.** `LIMIT/OFFSET` from `PageRequest`; worst page at 100k costs a few ms.
Keyset would break "jump to page N" that `MatPaginator` offers.

**D9. Frontend: URL is the single source of truth.** `OwnerListComponent` subscribes once to
`ActivatedRoute.queryParams`, normalises them (defaults `page=0,size=10,sort=NAME,dir=asc`),
and `switchMap`s to `OwnerService.getOwnersPage(params)`. Sort-header, paginator and search
events only call `router.navigate([], {queryParams, queryParamsHandling:'merge', replaceUrl:
true})`; the search handler sets `page: 0`. `switchMap` cancels in-flight requests, which is
the race fix. Alternatives: component-local state with a `BehaviorSubject` (loses refresh and
deep links); `mergeMap` (stale paints).

**D10. Grid widgets.** `MatTableModule`, `MatSortModule`, `MatPaginatorModule` added to
`OwnersModule`; `matSort` with `matSortDisableClear` on the table, `mat-sort-header` only on
the Name and City columns, `mat-paginator [length]="totalElements" [pageSizeOptions]="[5,10,20]"`.
Server-side mode: no `MatTableDataSource` sorting/paging, the `dataSource` is the page's
`content`. Keep `id="ownersTable"` and `td.ownerFullName` so the existing glue selectors hold.

**D11. `ownerName` pipe.** `shared/owner-name.pipe.ts`, `@Pipe({name:'ownerName', pure:true})`,
declared/exported from a small `SharedModule` imported by the owners, pets and visits modules.
Applied to the six templates that render `{{ x.firstName }} {{ x.lastName }}` for an owner
(vet-list renders vets and is left alone).

**D12. Errors on the grid fetch propagate.** `OwnerService.getOwnersPage` has no
`catchError`; the interceptor already toasts, and the component keeps its last page. The other
`OwnerService` methods keep `handlerError` (out of scope).

**D13. e2e glue.** `owners-grid.feature` + glue own the sort/size/walk scenarios;
`owner-search.feature.glue.ts` changes exactly four things: `data.content`, `fullName` →
`"Last, First"`, `namesIn` splits on `;` (and the Examples cells switch to `;`), and the
"every owner" step walks pages by driving the paginator's next button and asserting the sorted
union. Both features stay read-only on the DB, per `petclinic-test/AGENTS.md`.

**D14. Proving the index.** `petclinic-backend/src/test/jmeter/` already holds a CRUD
benchmark; add a gitignored `scripts/gen-owners-100k.sql` generator (documented in
`petclinic-backend/docs/`), a JMeter plan hitting the last page sorted by name, and record
`EXPLAIN (ANALYZE)` output in the change's tasks as the acceptance evidence. Not run in CI.

## Risks / Trade-offs

- [ICU absent in Zonky] → migration falls back to default collation; the diacritic scenario is
  verified manually on dev Postgres and documented as not CI-covered. If ICU *is* present but
  behaves differently from production Postgres, `EXPLAIN` on the 100k set is the tiebreaker.
- [Changing `last_name`/`first_name` column collation touches every existing query on those
  columns] → `lastName` prefix filter (`LIKE 'Pot%'`) stays correct under ICU; it may stop
  using a future btree index unless that index carries the same collation — none exists today.
- [Breaking `GET /api/owners` for unknown consumers] → grep confirmed only the Angular list and
  the e2e glue read the array. **Verified (task 2.8):** the MCP tools (`PetClinicMcp`) and the
  chatbot's `AssistantFlowTest` only call `GET /api/owners/{id}` (single owner), never the list
  endpoint — no other backend or chatbot consumer needs adapting.
- [Guardrail races] → regenerate `openapi.yaml`, `api-types.ts`, `ApiExamples.OWNERS` and the
  wiremock mapping in the same commit as the controller change; never run a partial Maven suite
  after a full one before committing (jacoco.csv trap).
- [`replaceUrl:true` on every param change] → back button leaves the owners page in one step;
  accepted, the alternative floods history with every page click.
- [Two `Page` shapes] → Spring's `Page` JSON also carries `pageable`, `sort`, `first`, `last`
  etc.; the spec names only the five fields clients rely on. Consider `PagedModel`/a small
  `PageDto` if the OpenAPI extractor produces an unreadable schema — decide when the generated
  `openapi.yaml` is first inspected.

## Migration Plan

1. Backend lands first (migration `V9`, controller, DTO, advice, regenerated `openapi.yaml`
   and `ApiExamples`), with the slice test green.
2. Frontend + e2e glue land in the same PR, since the array shape is gone the moment the
   backend deploys; the wiremock mapping lets the frontend be developed against the new shape
   before the backend is running.
3. Rollback: revert the PR. `V9` only adds indexes and a collation; leaving them in place on
   rollback is harmless.
4. Post the decision comment on issue #25 once the PR is open.
