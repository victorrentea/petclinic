# Design

## Context

See [proposal.md](proposal.md) for why and [QA.md](../../../QA.md) for the decisions taken in the
grill-me session. Current state that shapes the approach:

- `OwnerRestController.listOwners` → `OwnerRepository.findByLastNameStartingWith(String)` → `List<OwnerDto>`.
  `OwnerRepository` extends the bare `Repository` interface (no `findAll(Pageable)` inherited).
- `Owner.pets` and `Pet.visits` are both `LAZY`; no batch fetching is configured. Mapping a page of
  20 owners would run ~1 + 20 (pets) + N (visits) queries.
- The database collation is `C.UTF-8` (byte order). ICU collations exist in the embedded Postgres
  16.2 on macOS (`und-x-icu` verified on the dev database).
- `owners` has no index besides the primary key.
- Errors are rendered by `ExceptionControllerAdvice`; `ValidationException` and
  `ConstraintViolationException` already map to 400 + `ProblemDetail`. Anything else is a 500.
- The frontend already depends on `@angular/material` 16.2; `MatPaginator`/`MatSort` are unused so far.
  An unused `OwnerPage` interface with the target field names already exists.

## Goals / Non-Goals

**Goals:**
- A page of owners costs a constant number of SQL statements, independent of page size.
- Every sort the API accepts is served by an index at 100k owners.
- The REST contract stays explicit and small: no Spring Data type leaks into `openapi.yaml`.

**Non-Goals:**
- Slimming the list payload (owners still carry pets with visits).
- Case-insensitive or accent-insensitive search.
- A reusable paginated-table component in `design-system/`.
- Fixing the deployment diagram's missing AI-agents → `/mcp` arrow (QA.md Q25): it goes to `main` separately.

## Impact

**API contract — BREAKING.** `GET /api/owners` returns one page object
`{content, totalElements, totalPages, number, size}` instead of a JSON array. New query params:
`page` (0-based, ≥ 0), `size` (5 | 10 | 20, default 10), `sort` (`name` | `city`, optional `,asc` | `,desc`,
default `name,asc`); any other value → 400 `ProblemDetail`. `lastName` keeps its case-sensitive
prefix semantics. Only the frontend calls this endpoint, and it ships from the same monorepo; the
chatbot and the AI agents reach the backend through `/mcp`, whose tools list no owners.

**Code.**
- Backend: `OwnerRestController.listOwners`, `OwnerRepository`, new `rest/dto/OwnerPageDto`,
  `OwnerMapper`, a sort-key enum, `application.properties` (batch fetching).
- Frontend: `OwnerService`, `OwnerListComponent` + template, `OwnersModule`
  (`MatPaginatorModule`, `MatSortModule`), the existing unused `owner-page.ts`.
- `openapi.yaml` is regenerated by `OpenApiExtractorTest`.

**Data.** New Flyway migration `V4__owners_icu_collation.sql`: schema only (collation on three
columns + three indexes); reference and seed rows untouched.

**Tests to update.** `OwnerTest`, `AddVisitApiTest`, `OwnerSearchThroughLatencyProxyTest`,
`BasicAuthenticationConfigTest` (if it reads the body), Cucumber `owners.feature` + `OwnerSteps`,
Playwright `owner-search.feature` — its "every owner in the clinic is listed" scenario cannot hold
with 27 seeded owners and a page size of 10.

**CI / deploy.** The `und-x-icu` collation must exist in the embedded Postgres on the Linux CI runner
and in production Postgres — see Risks.

## Decisions

### D1. Explicit `page`/`size`/`sort` request params, not a `Pageable` controller argument
`listOwners(lastName, page, size, sort)` validates each value and builds the `PageRequest` itself.
*Why:* Spring's `Pageable` resolver silently clamps an oversized `size` instead of rejecting it, and
an unknown sort property surfaces as `PropertyReferenceException` → 500. It would also let clients sort
by any entity path (`pets.visits.description`), bypassing the indexes.
*Alternative:* `Pageable` + `@PageableDefault` + a custom validator — more magic for the same result.

### D2. A whitelist enum maps API sort keys to entity orderings
`name` → `lastName, firstName, id`; `city` → `city, id`. The direction applies to every column
including `id`. Parsing `"<key>[,asc|desc]"` is done by the enum; an unknown key or direction throws
`ValidationException` → 400 via the existing advice. Size ∉ {5,10,20} or page < 0 → same path.
*Why:* the API vocabulary (`name`) is decoupled from entity fields, and the trailing `id` gives a
total order, so pages are stable.

### D3. Hand-written `OwnerPageDto` in `rest/dto/`
Fields `content: List<OwnerDto>`, `totalElements`, `totalPages`, `number`, `size` — identical to the
frontend's `owner-page.ts`. Built from Spring's `Page<Owner>` by `OwnerMapper`.
*Why:* house rule (hand-written DTOs), and Spring Data warns that serialising `PageImpl` directly
yields an unstable JSON shape.

### D4. Repository: `Page<Owner> findByLastNameStartingWith(String lastName, Pageable pageable)`
A derived query on the bare `Repository` interface; Spring Data issues the count query itself. The old
`List` variant is removed if no other caller remains.

### D5. ICU collation on the columns, via Flyway `V4__owners_icu_collation.sql`
```sql
ALTER TABLE owners
  ALTER COLUMN first_name TYPE TEXT COLLATE "und-x-icu",
  ALTER COLUMN last_name  TYPE TEXT COLLATE "und-x-icu",
  ALTER COLUMN city       TYPE TEXT COLLATE "und-x-icu";
CREATE INDEX owners_name_idx        ON owners (last_name, first_name, id);
CREATE INDEX owners_city_idx        ON owners (city, id);
CREATE INDEX owners_last_name_like_idx ON owners (last_name text_pattern_ops);
```
*Why:* every query (REST, MCP, future reports) then sorts identically with plain `ORDER BY`, and
Spring's `Sort` needs no native SQL. `und` (root locale) suits mixed European names; `ro-x-icu` would
mis-sort Polish. The `text_pattern_ops` index keeps the `LIKE 'Pot%'` filter indexable, since a
non-C collation can't serve prefix matches from a default btree.
*Alternative rejected:* `ORDER BY … COLLATE` per query (needs `JpaSort.unsafe`/native SQL and
expression indexes; the rule lives in Java instead of the schema).

### D6. Global Hibernate batch fetching instead of `@BatchSize` on one association
`spring.jpa.properties.hibernate.default_batch_fetch_size=20` in `application.properties`.
*Why:* both `Owner.pets` and `Pet.visits` are lazy; one setting turns each level into one `IN (…)`
query, so a page costs ~4 statements (page, count, pets, visits) regardless of size. Refines
QA.md Q14, which named only `Owner.pets`. Never `JOIN FETCH` + `Pageable` (HHH90003004: in-memory paging).

### D7. Frontend: Material paginator + sort on the existing table, URL as the source of truth
`OwnerListComponent` reads `lastName`, `page`, `size`, `sort` from the route's query params and
reloads on every change (`switchMap`, which also keeps "latest request wins"). Paginator/sort/search
events only `router.navigate` with new query params (`page` reset to 0 on search, sort or size
change). `mat-sort-header` only on Name and City. `OwnerService.getOwners(query): Observable<OwnerPage>`
replaces `getOwners()`/`searchOwners()`.
*Why:* one code path for initial load, Back, refresh and user interaction.

## Risks / Trade-offs

- [The embedded Postgres binaries on the Linux CI runner may lack ICU → `V4` fails, every backend
  test fails] → Task 1 runs the migration in CI before anything else is built on it; fallback is
  adding the Linux Zonky binary artifact matching 16.2 explicitly in the pom.
- [Production Postgres built without ICU] → same migration fails at deploy time; check
  `SELECT 1 FROM pg_collation WHERE collname = 'und-x-icu'` on the target before release.
- [ICU collation version drift after an OS/ICU upgrade can make indexes silently mis-ordered] →
  Postgres warns on collation version mismatch; `REINDEX` the three indexes when it does.
- [Breaking API change] → only the frontend calls `GET /api/owners`; both ship from this monorepo
  in one release.
- [`COUNT(*)` on every page request at 100k rows] → acceptable (index-only scan); revisit if the
  latency proxy test shows otherwise.

## Migration Plan

Deploy backend and frontend together. `V4` alters column collation (no table rewrite for `TEXT`, but
indexes on those columns are rebuilt) and creates three indexes — seconds at 100k rows. Rollback:
a `V5` reverting to `COLLATE "C"` and dropping the indexes; the previous frontend needs the previous
backend (array response), so roll both back together.
