Does the db-cli skill pay off?

Each task is answered by fresh headless Claude Code agents, in a copy of the repo with the skill and in one without it. Same prompts, same machine, interleaved, so both arms share the load and the rate limits.

{{META}}
How an eval works
  1. Task = a prompt with a known right answer, plus a known trap. A script grades every final answer (expected facts present, trap absent), so no human judges it.
  2. Arm = one variant of the setup. Here two copies of the same repo, identical except that one has the skill deleted. That one difference is the thing being measured: an A/B test.
  3. Runs: an agent is not deterministic. The same prompt takes a different route, time and cost on every try, so one run proves nothing. Each task is asked 7 times in each arm, and the arms are compared on the median (correct answers, seconds, $, tokens).
  4. Cost: {{COST}}. Every agent run is billed, and the bill grows as tasks × arms × runs. One pass is never the last one: every change to the skill, a prompt or a grading regex means running the whole matrix again.

How it was run

  1. docs/eval/db-cli/run.py builds two throwaway arms from git archive HEAD: with keeps .claude/skills/db-cli, without deletes it and the hint to it in .mcp.json. Both lose docs/eval/ (the expected answers and past ones live there) and become fresh one-commit repos, so the agent can't git show the skill back.
  2. Every run is a fresh claude -p in one arm: --setting-sources project, no MCP server at all (--strict-mcp-config with an empty config), bypassPermissions, no session persistence, a $3 budget cap, and the parent's CLAUDE* env vars stripped. The shell is the only way into the local Postgres.
  3. Jobs are interleaved (run i of every task, both arms, then run i+1), 6 in parallel. Each writes a stream-json log.
  4. report.py grades each final answer with the regexes in tasks.json (all expected facts present, trap absent), reads tokens, cost and duration from the result event, and classifies the route from the Bash commands. pretty_report.py renders this page from the same parsing.
